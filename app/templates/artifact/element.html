WHICH ARTIFACT, AND WHICH GENERATOR. This file belongs to the FIRST of the project's two HTML contracts, and the two are never collapsed into one. cucumber-java 7.2.3 (pom.xml, retained as historical reference) pulls html-formatter 17.0.0, which produced target/cucumber-reports.html - one self-contained page carrying no external asset reference of any kind. That page is what app/reporting/html_report.py writes and what the templates in this folder describe. The report tree under target/cucumber/ comes from a different generator - cucumber-reporting 5.6.1 over Velocity - and owns its own page set, layout, assets and navigation in app/templates/pretty/. Nothing here is shared with that folder except the three partials named below, and no template from it is imported or mirrored here. WHY THIS TEMPLATE RENDERS THE RESULTS AT ALL. In the committed reference artifact the content container is EMPTY: the whole report travels as a client-side message payload rendered at load time by a bundled script of 1,381,454 characters. This port does not reproduce that, because the plan's acceptance criterion for this artifact is its opposite - every feature, scenario, step, status, timestamp and embedded screenshot from the input result set has to be present in the DOM, checked against a generated baseline for page structure. A client-side shell has none of it in the DOM. The departure is the plan's own authorised deviation for both HTML outputs being generated from this project's templates and accepted structurally. This template is the part that puts scenarios and steps in the document, so it emits neither that payload nor that bundle, and no script of its own. --------------------------------------------------------------------------- THE MACRO --------------------------------------------------------------------------- {% from "artifact/element.html" import element_block %} {{ element_block(element, findex, eindex) }} element REQUIRED. A per-feature id scheme is correct there and silently broken here: it yields duplicate id attributes, invalid markup, and toggles that expand the wrong region. So every id this file emits, and every uid it hands the step partial, is composed from the feature index, the element index and the step's position - never from a step name, never from a bare loop counter, and above all never from the scenario or feature id slug, because TWO PAIRS OF FEATURES SHARE AN id: two are titled "Testinium app Inventory feature" and two "Testinium app login feature". The plan preserves that collision rather than disambiguating it, which is also why the viewer's routes key on index; the same reasoning binds this template. Two ids are emitted per element, both derived and both stable for identical input: one on the root, which gives every scenario a fixed anchor inside the single document, and one on the steps region, which the toggle names through its controls attribute. The steps region's id is emitted only when there are steps for it to hold, so no control ever points at nothing. --------------------------------------------------------------------------- SCREENSHOTS --------------------------------------------------------------------------- Capture is failure-only, happens once per scenario and happens before the driver is disposed of, and a capture that fails is logged and suppressed. A FAILED SCENARIO CARRYING NO SCREENSHOT IS THEREFORE THE NORMAL CASE - the reference report carries no embedding, no hook list and no output anywhere, which corroborates the plan's finding that the original teardown hook never ran at all. The lightbox partial renders nothing for an empty input and leaves no node behind, and this file calls it once into a variable and emits the result only when it is not blank, so no empty figure or dangling caption can survive. An embedding is scenario-level data - it is attached in the after hook and named with the scenario's own name - so it is rendered once at element level, after the steps, and is deliberately NOT also handed to a step: a base64 payload rendered twice would double the artifact's weight for no reading gain. Both a flat embedding list and the after-hook list are accepted, because the partial flattens one level of nesting, and the image is always an inline data URI. No image element is built here. The after hook's own result is not rendered. The JSON writer owns that field; this page reports the scenario and its steps. --------------------------------------------------------------------------- STANDING PROHIBITIONS --------------------------------------------------------------------------- This markup is inlined into a page that must open from a workspace with no network at all, so, with no exception: no absolute, protocol-relative or content-delivery-network address; no stylesheet, behaviour-script, image or sibling-page reference; no application endpoint address and no call to the framework's address builder, since this template is rendered to a file rather than served; and the only address permitted on the page is an inline data URI, which only the lightbox partial emits. This file inherits no shell template - the shell resolves its own assets through that builder, which would break self-containment outright - and contains no inline script and no inline style, because behaviour belongs to app/static/js/report.js and presentation to app/static/css/main.css, which the writer inlines.
