{#- =========================================================================== view/overview.html - the run overview, served read-only at GET /reports. =========================================================================== This page is the HTTP analogue of the "Features Statistics" overview page in the generated report tree: one table of every feature in the results, with its step tally, its scenario tally, its duration and its status, each feature linking on to its own detail view. It reads what a run has already written and nothing else - no form, no control that starts a run, no endpoint of its own invention, and no write of any kind. Runs start from the command line. --------------------------------------------------------------------------- RENDER CONTEXT - the contract for app/web/routes.py --------------------------------------------------------------------------- REQUIRED features The top-level list parsed from the Cucumber results file, IN FILE ORDER, each entry the raw feature mapping exactly as the JSON writer produced it. Nothing is pre-processed and no aggregate is pre-computed: every count, status and total on this page is derived below, from that one list, so the page and the artifact it describes cannot drift apart. Its ZERO-BASED POSITIONS ARE THE ROUTE KEYS. The feature route is keyed by index and never by the feature's own id, because two pairs of features in this suite share an id slug - they share a title - and that collision is source behaviour this port preserves rather than disambiguates. An id rendered as displayed data is correct; an id used as a link key is a defect. Every URL here is built with url_for, so no route shape is written by hand in markup. OPTIONAL artifact_modified Modification time of the results file this page was built from, as millisecond-precision UTC ISO-8601 with a literal Z - the same shape the scenario start timestamps carry, so both render through the same machine-readable time element. Absent renders an em dash. WHAT THE ROUTE MUST NOT DO - it must not hand this template an empty or unusable result set as a 200. A results file that is absent, unreadable or unparseable is a 404 for all three causes alike, because a run has not produced usable results and telling those causes apart is not the viewer's business. So there is deliberately no "no report yet" state here; that belongs to the index view, which answers 200 always and owns the artifact availability listing. The ONE empty state that is genuinely reachable is an empty feature LIST: a run whose tag expression selected no scenario still writes all four artifacts, so `features == []` renders cleanly, with the tallies at zero and the table replaced by a short factual note. --------------------------------------------------------------------------- THE MODEL, AS MEASURED --------------------------------------------------------------------------- Every shape below was read off the reference results file, not assumed, and each one is guarded for because each one occurs: - A feature carries uri, id, keyword, line, name, description, tags and elements. uri keeps its literal file: prefix and is displayed verbatim - never stripped, rewritten or turned into a filesystem link. - Feature tags and scenario tags have DIFFERENT shapes: a feature tag is a mapping of name, type and location, a scenario tag carries name alone. Only name is read, and the leading @ is kept. - A scenario with no tags of its own and no feature tag OMITS the tags key entirely rather than carrying an empty list, and five of the ten features in this suite declare no feature-level tag, so that is the common case and not an edge one. - elements INTERLEAVES backgrounds and scenarios, and the background REPEATS before each scenario. A background carries no id, no start_timestamp and no tags. So a feature's scenario count is the number of elements whose type is "scenario" and NEVER the element count. - A step carries keyword (with its trailing space), line, name, match and result. - result OMITS fields rather than emitting zeros: a skipped step's result is a status and no duration key at all. Durations are NANOSECOND INTEGERS, which is why the raw value never reaches the page. --------------------------------------------------------------------------- AGGREGATION RULES - one definition, three consumers --------------------------------------------------------------------------- These same rules are what view/feature.html applies to one feature and what GET /reports/summary MUST APPLY IN PYTHON. The JSON counts route and this page are two presentations of one calculation, so a reader comparing them can never be shown two different answers: 1. Step counts Every step of every element is counted, backgrounds included, because a repeated background genuinely ran once per scenario. Each step's status is normalised through status_token, the project's single normalisation point. 2. Scenario The worst status among that scenario's OWN steps, by the status precedence in STATUS_PRECEDENCE below, highest first: failed, undefined, ambiguous, pending, skipped, untested, passed. A scenario with no steps is unknown. 3. Feature The same precedence applied across the steps of ALL that status feature's elements, backgrounds included. 4. Duration The sum of the duration values that are PRESENT, in nanoseconds, rendered as seconds to three decimals. With no duration key present at all the total is unknown rather than zero, and renders an em dash. 5. Earliest The lowest start_timestamp present across scenario start elements. These strings compare lexicographically because the format is fixed-width UTC. None present renders an em dash. The table's step columns mirror the reference overview page exactly - passed, failed, skipped, pending, undefined, total - so a step in one of the three remaining states is inside its feature's total without a column of its own. The run-level tallies above the table carry every non-zero state, including those three, so nothing is dropped from the page. --------------------------------------------------------------------------- VOCABULARY AND PROHIBITIONS --------------------------------------------------------------------------- HEADINGS - base.html renders this page's single h1 from the title block, so the content below opens at h2 and descends without skipping a level. LAYOUT - the page carries each feature TWICE, and deliberately: once as a row of the statistics table, which mirrors the reference overview page's columns, and once as a block below it holding the values that describe a feature rather than count it - its source, identifier, line, first start, tags and description. Those values are not squeezed into the table, because the table is wider than a phone viewport and scrolls inside its own wrapper: a cell spanning its columns inherits that width, so a source path or a description placed there is clipped until the reader scrolls sideways, whatever the cell does internally. In page flow the same values reflow to the viewport. The two elements of one feature carry the same status hooks and the same index-keyed link, so they filter together and navigate alike. CLASSES - app/static/css/main.css, the tqa- namespace, and only names that stylesheet declares: tqa-meta and its item, label and value parts, tqa- summary with tqa-count, tqa-filter with tqa-filter-btn, tqa-table-wrap with tqa-table, tqa-feature with tqa-feature-name and tqa-feature-desc, tqa-tags with tqa-tag, tqa-timestamp, tqa-duration, tqa-link and tqa-empty. Status colour arrives only as the data-tqa-status attribute, which the stylesheet matches case-insensitively; there is no per-status class to write. The page shell classes belong to base.html and are not repeated here. Two placements follow that stylesheet rather than the page order alone. The metadata grid resolves to four columns at its widest, so a feature block fills it with exactly four short fields and keeps its one long value - the source path - at full width, where no fixed track can break it mid-word and strand a character on a line of its own. And the fields whose own margins space them are ordered so each has room: the flex heading, then the description, then the grid, then the source line, which is last because it is the only one with no bottom margin of its own. BEHAVIOUR HOOKS - app/static/js/report.js, the data-report- namespace. This page uses three: data-report-filter on each filter button, and the data- report-filterable and data-report-status pair on each element the filter may hide - one table row and one block per feature. Both carry the same status, so a feature hides as one unit. The one per-page scope hook that script resolves filtering against is emitted by base.html, on the main element, and is never repeated here. Filtering is progressive enhancement: with no scripting the buttons are inert and everything stays visible. NO STATE HOOK IS SERVER-RENDERED. The stylesheet reads the absence of its three boolean state attributes as expanded, visible and closed, and report.js sets its own three state classes at run time, writing aria-pressed="false" onto every filter control as it initialises. What is authored here is therefore the fully visible, unfiltered page, which is exactly what it means with scripting turned off and on paper. Standing prohibitions, each with its reason: automatic escaping is never turned off and no value is ever marked pre-escaped, because feature descriptions, step names and assertion text in this data carry quotes, apostrophes and angle brackets - the stylesheet's pre-wrap rules preserve multi-line text and leading indentation without any such override. No inline script, no inline style and no style attribute. No external, protocol- relative or content-delivery-network URL, and none of the vendored generator assets, which exist only inside the emitted report tree.
