Only name is read, and the leading @ is kept. - A scenario with no tags of its own and no feature tag OMITS the tags key entirely rather than carrying an empty list, and five of the ten features in this suite declare no feature-level tag, so that is the common case and not an edge one. - elements INTERLEAVES backgrounds and scenarios, and the background REPEATS before each scenario. A background carries no id, no start_timestamp and no tags. So a feature's scenario count is the number of elements whose type is "scenario" and NEVER the element count. - A step carries keyword (with its trailing space), line, name, match and result. - result OMITS fields rather than emitting zeros: a skipped step's result is a status and no duration key at all. They are restated here as documentation of what the values in the context MEAN, not as instructions this file carries out - and if any statement here ever disagrees with that module, that module is right: 1. Step counts Every step of every element is counted, backgrounds included, because a repeated background genuinely ran once per scenario. A HOOK IS NEVER A STEP, and no hook's duration is ever added. 2. Element The severity fold over that element's OWN steps AND ITS status OWN HOOKS, highest first: failed, undefined, ambiguous, pending, skipped, untested, passed. So a scenario whose steps all passed but whose after-hook failed is not reported as a pass. An element with neither steps nor hooks is PASSED - the reference generator's measured rendering of the step-less Background in EmployeeFc.feature - and unknown is kept for a status the model never produced. 3. Feature The same fold over that feature's element statuses, status backgrounds included, so a background-only failure moves the feature's status without moving any scenario's. A feature carrying no element at all is unknown: nothing ran. 4. Duration The sum of the STEP duration values that are present and usable, in nanoseconds, rendered as seconds to three decimals. Usable is a non-negative integer that is not a boolean, which is the same predicate the step partial renders by, so a total can never count a sample a step row declines to show. With no usable sample at all the total is unknown rather than zero, and renders an em dash. 5. Earliest The lowest PARSEABLE start_timestamp across scenario start elements, returned verbatim. A value that does not parse is dropped rather than displayed, so this page can never show a timestamp GET /reports/summary reports as null. 6. Scenarios Elements whose type is "scenario", and never the element count: backgrounds interleave and repeat. The table's step columns mirror the reference overview page exactly - passed, failed, skipped, pending, undefined, total - so a step in one of the three remaining states is inside its feature's total without a column of its own.
