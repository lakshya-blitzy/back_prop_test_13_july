WHERE THE CONTRACT ACTUALLY LIVES --------------------------------- app/reporting/screenshots.py is the authority, and it is a SERVER-SIDE STRUCTURAL VALIDATOR, not a signature test: it decodes the payload and establishes PNG's signature, an IHDR first chunk of the specification's thirteen bytes, non-zero dimensions inside a dimension and a pixel budget, a colour-type and bit-depth pairing the format defines, a CRC-checked walk of every chunk, at least one IDAT, a terminal zero-length IEND with NOTHING after it, and image data that inflates - under a bounded budget - to exactly the size its own header declares. Every attachment that reaches any of the three surfaces has been through it, because the two report writers normalize through app/reporting/aggregation.py and the JSON writer normalizes in app/reporting/cucumber_json.py. A TEMPLATE CANNOT DECODE BASE64, so the tests below are necessarily a STRICTLY WEAKER RULE and are DEFENCE IN DEPTH ONLY. The relationship is one-directional and is asserted in tests/test_png_embedding_contract.py: whatever the authority accepts, this guard must accept; whatever this guard rejects, the authority must reject. It exists for the case the authority cannot cover - a page rendered from a result set that never passed through it - and it must never be mistaken for the control that makes an attachment safe. BASE64_CHARS is the standard alphabet plus the padding sign - the set a canonical payload's characters are drawn from, and deliberately NOT the URL-safe alphabet, whose "-" and "_" are a different encoding. PNG_BASE64_HEADER is the base64 prefix that establishes PNG's whole OPENING HEADER rather than its signature alone. Every valid PNG begins with the same SIXTEEN bytes: the eight-byte signature 89 50 4E 47 0D 0A 1A 0A, then 00 00 00 0D - the length of the first chunk, which the format fixes at IHDR's thirteen bytes - then the four characters IHDR. Base64 maps each three bytes onto four characters, so fifteen of those sixteen bytes encode as exactly twenty characters with no bits of a later byte mixed in, and those twenty characters are identical in every PNG that exists. Requiring twenty rather than eleven is what this guard gained, and it is not cosmetic: eleven characters pin the signature and nothing after it, so "iVBORw0KGgo=" - the signature alone, with no header, no image data and no IEND - satisfied them and became an image data URI. It cannot satisfy twenty. The eight-character prefix is weaker still, pinning only six bytes, so a payload agreeing in six is base64 of something that is not a PNG at all. The authority asserts this constant against genuine PNG encodings, including a real browser capture, rather than trusting the arithmetic. PAD1_TAIL_CHARS and PAD2_TAIL_CHARS are the canonicality test a character scan cannot otherwise make. A payload ending in one "=" carries six unused bits in its last data character, and a payload ending in "==" carries four; canonical base64 requires those bits to be zero, so the preceding character must come from the subset whose value is a multiple of four or of sixteen respectively. Without this, iVBORw0KAB== passes - and its bytes canonically encode as iVBORw0KAA==, so a reader has two spellings of one payload to reconcile. MIN_BASE64_CHARS and MAX_BASE64_CHARS mirror the authority's own bounds at the encoded lengths that imply them: the smallest structurally complete PNG is its signature plus an IHDR, an IDAT and an IEND chunk, which is 57 bytes and therefore 76 characters; the largest payload accepted is 16 MiB of base64, which is the same limit the per-worker result schema in app/reporting/events.py enforces on the string it loads. -#} {%- set BASE64_CHARS = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/=' -%} {%- set PNG_BASE64_HEADER = 'iVBORw0KGgoAAAANSUhE' -%} {%- set PAD1_TAIL_CHARS = 'AEIMQUYcgkosw048' -%} {%- set PAD2_TAIL_CHARS = 'AQgw' -%} {%- set MIN_BASE64_CHARS = 76 -%} {%- set MAX_BASE64_CHARS = 16777216 -%} {#- The id the overlay's caption carries, so the script can point the dialog's description at it.
