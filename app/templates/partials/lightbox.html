It renders a failure screenshot that is already carried in the normalized result model as base64 text, together with the overlay that shows that screenshot enlarged. Screenshot presentation is its whole concern; nothing else belongs in this file. THREE SURFACES, ONE OUTPUT -------------------------- Every macro below is rendered into all three of the port's output surfaces, whose asset rules are mutually incompatible: artifact/*.html inlined into the single self-contained page written to the reports HTML artifact, which carries no external asset reference of any kind - the reference artifact has exactly one reference in 1,440,365 bytes, and it is an inline data URI pretty/*.html written into the generated report tree and opened straight from a continuous-integration workspace off the local filesystem, where every reference must resolve inside that tree view/*.html served over HTTP by the read-only viewer, which resolves its own assets in base.html and not here Exactly one image source satisfies all three at once, so the rule is absolute: THE SCREENSHOT IS ALWAYS AN INLINE DATA URI. Never a file path, never a route, never a URL produced by the framework's static-asset URL builder, never a remote host. The base64 payload travels inside the markup and is emitted verbatim - never truncated, rewrapped or reformatted, and never broken across lines inside the attribute value. =========================================================================== THE EMBEDDING CONTRACT: A VALIDATED PNG, AND NOTHING ELSE =========================================================================== The values below are RESULT-CONTROLLED. They arrive from a scenario's own after-hook list, and this macro is the one place in the project that turns them into a data URI - a URI the browser will fetch and decode. That makes this the trust boundary for the whole screenshot path, so the shape is checked here rather than assumed, and the media type in the emitted URI is a FIXED LITERAL rather than the value that arrived. An embedding is rendered only when every one of these holds: mime_type equals "image/png", compared case-insensitively after trimming. The plan's embedding shape is that media type and no other. A wider test - any image/ subtype - admits image/svg+xml, and an SVG is not a raster screenshot but an active document that can carry script, style and external references, none of which belongs in a report page that is otherwise guaranteed to reference nothing. data is canonical standard base64: every character drawn from the base64 alphabet plus its padding sign, a length that is a multiple of four, and padding only at the very end. A payload that is not base64 at all cannot be an image, and emitting it would produce a broken image where a reader expects failure evidence. data begins with the eight characters that are the base64 encoding of the PNG signature. Base64 maps three bytes to four characters, so the first eight characters of the encoding of any byte string are fixed by its first six bytes; a PNG always begins 89 50 4E 47 0D 0A 1A 0A, so those eight characters are the same for every PNG that exists. Requiring them rejects base64 of something that is not a PNG, which the declared media type alone cannot. Anything failing any of those renders the EMPTY STRING - no thumbnail, no placeholder, no broken image, and above all no data URI. The behaviour script applies the identical test before it will open an overlay, so the two cannot disagree, and the emitted URI's prefix is written out here as a literal so the media type cannot be influenced from the result at all. The checks are whole-string operations rather than a character loop: a screenshot payload runs to hundreds of thousands of characters, and a per-character template loop over one would cost more than rendering the rest of the page. Stripping the allowed characters from both ends and asking whether anything is left is exactly the test "every character is allowed", at the cost of one scan. THE INPUT MODEL --------------- One embedding mapping, as the result model carries it: mime_type the attached media type; only image/png is rendered data the base64 payload, already encoded name the scenario name, used as the caption and the alt text Capture is failure-only, happens once per scenario and happens before the driver is disposed of. A capture that fails is logged and suppressed, so a FAILED SCENARIO CARRYING NO EMBEDDING IS A WHOLLY NORMAL STATE: every macro here renders the empty string for it - no placeholder, no "unavailable" message, no empty container element and above all no broken image. STATE, AND WHY NONE OF IT IS SERVER-RENDERED -------------------------------------------- The overlay ships CLOSED and the page ships fully visible. The stylesheet reads the absence of the report script's three runtime state classes as expanded, visible and closed, and the script adds them when the reader acts; this file emits none of them, so server output always describes the no-scripting state and stays correct with scripting disabled and on paper. Nor does this file emit any attribute that would keep the overlay out of the accessibility tree or out of the rendered page: the report script manages the visibility mirror itself, and a second mechanism here could leave an overlay that the script opens and the browser still refuses to show. The overlay image is deliberately emitted with NO source attribute at all - not a placeholder, not a single-pixel image. The script writes the source when it opens the overlay, copying it from the thumbnail that was clicked, and removes it again on close. THERE IS NO BACKDROP ELEMENT. The overlay container is itself the full-viewport layer the stylesheet dims, and a click whose target is that container is the dismissal. An earlier revision emitted an empty child to give the script a precise target; as a flex child with no content and no rule of its own it had no size at all, so it could never be clicked, and the hook it carried was dead the moment it was written. WHAT THIS PARTIAL DELIBERATELY DOES NOT OFFER --------------------------------------------- No enable or disable affordance for screenshots, in any form. The project documentation claims screenshots can be switched on, but no setting and no branch in the teardown hook ever provided one, so the claim is aspirational and the configuration surface stays at its six keys. No download control, no open-in-a-new-tab control and no external image host: each would add a link reference and break the self-contained artifact. No icon font for the close control - the vendored icon fonts reach only the generated report tree and would render as an empty box in the other two surfaces - so the glyph is a character reference. No inline style attribute and no embedded stylesheet block: presentation belongs to main.css, which one writer inlines and the other copies. No class outside the set main.css declares, which is why the caption element carries only its behaviour hook. And none of the vendored generator's own collapse attributes: the report script is the single owner of interactivity across all three surfaces. ESCAPING -------- Jinja's automatic HTML escaping is relied on for every interpolated value, and no value is ever marked as trusted markup. Scenario names carry apostrophes and quotation marks, and assertion text carries angle brackets, so this matters in the alt attribute, the button's accessible name and the caption. The base64 payload needs no escaping by construction: its alphabet is letters, digits, plus, slash and the padding sign, none of which the escaper rewrites, so the payload survives a round trip byte for byte - and the contract above has already established that it contains nothing else.
