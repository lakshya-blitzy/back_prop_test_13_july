Every handler therefore lives in app/errors.py at application scope, and this template is what the not-found handler renders. Validation criterion V11 grades precisely that - an unknown route answered by the application-level handler "so it actually fires", instead of the framework's own default error page. ONE TEMPLATE, TWO STATUS CODES. AAP 0.2.1 and 0.3.1 fix this folder at exactly two files, 404.html and 500.html. A method-not-allowed response has no template of its own and none may be added - AAP 0.8 is binding: "No feature may be dropped, and none may be added" - so a non-API 405 is answered with this page too. The copy below is therefore deliberately status-agnostic: it names no status code and no digit, which keeps it factually correct for either response the handler sets. For the same reason there is no status-keyed hook for the stylesheet to hang a rule on, and section 14 of static/css/main.css documents the matching decision on its side. NOTHING HERE CAN RAISE, BY CONSTRUCTION. An exception while rendering an error page is the worst failure mode available: it turns a 404 into a 500, or sends the 500 handler round again. Two consequences, both intentional: - Not one context variable is read. This page renders identically whether the handler passes a full context or nothing at all, so no missing name and no undefined attribute can break it. - Both links below are literal root-mounted paths, "/" and "/reports", the two fixed by AAP 0.3.1. Deriving them from blueprint endpoint names would raise a build error - and so a 500 - the moment an endpoint is renamed. The shared layout takes the same approach for the same reason. NOTHING DIAGNOSTIC REACHES THE READER.
